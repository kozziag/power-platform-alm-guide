Why ALM matters

Application Lifecycle Management keeps your production Power Apps and Power Automate flows stable while you keep building and testing. Instead of editing live apps directly in production, you build in an isolated Development environment, package your work into a Solution, and use a Pipeline to promote it safely to Test and eventually Production.

Microsoft's current (2026) recommended approach for this is:

  • Solutions — the container that holds your apps, flows, tables, and other components
  • Power Platform Pipelines — the built-in, no-code deployment tool that moves solutions between environments in a few clicks
1 Create a Solution (not the Default Solution)
  1. Go to make.powerapps.com and select your Development environment from the environment switcher (top right).
  2. In the left navigation, select Solutions → + New solution.
  3. Enter a Display name (e.g. ALM Demo Solution).
  4. Click + New publisher and provide:
    • Display name (e.g. ALM Demo Publisher)
    • Name (e.g. ALMDemoPublisher)
    • A short Prefix (e.g. almdemo)
    Click Save.
  5. Click Create.
Why a custom publisher? The prefix tags every component you build (e.g. almdemo_MyTable) so it never collides with Microsoft's or another publisher's component names.
2 Build everything inside that Solution

Inside your new solution, click New and choose what you want to build:

  • App — Canvas or model-driven app
  • Automation → Cloud flow — Power Automate flow
  • Table — Dataverse table
Never build loose components in the "Default Solution." Anything outside a named solution cannot be reliably exported or promoted between environments.
3 Set up a Pipeline

Power Platform Pipelines is Microsoft's modern, no-code ALM tool — it replaced manual export/import. It's enabled tenant-wide by default (the "platform host"), so no admin setup is required for personal use.

  1. Open your solution → left navigation → Pipelines tab.
  2. Click Create new pipeline.
  3. Give it a name (e.g. Dev to Test).
  4. Source Environment automatically fills in as your current (Dev) environment.
  5. Choose your Target Environment (your Test or sandbox environment) from the list.
  6. Click Save.
4 Deploy
  1. On the Pipelines screen, click Deploy here under your target environment's card.
  2. Confirm the pipeline, target, and schedule (choose Now) → click Next.
  3. Review the summary — the version number auto-increments (e.g. 1.0.0.0 → 1.0.0.1) and an AI-generated deployment note is included.
  4. Click Deploy.
  5. Wait roughly 30–60 seconds. Status will update to "Last successfully installed version X.X.X.X".
✅ Verified: deployment completed successfully in a live test run of this exact guide.
5 Verify in the target environment
  1. Switch to the target environment.
  2. Go to Solutions → filter by Managed.
  3. Your solution appears there as read-only/managed.
You cannot edit components directly inside a Managed solution. All future changes happen back in Dev, then get redeployed through the pipeline.

Golden Rules to keep ALM healthy

  • Always build in Dev (unmanaged), always deploy as Managed downstream.
  • Never edit components directly in a Managed environment — edit in Dev, then redeploy through the pipeline.
  • Keep Dev / Test / Production as separate environments — one Dataverse database per environment.
  • Use the same publisher and prefix for a given solution across its entire lifecycle.
  • For multiple developers or solutions, consider adding source control (Git) via the Pipelines "Source control" tab for full version history.
